## Problem Statement

India's small online sellers (Meesho resellers, Instagram/WhatsApp shops, first-time Amazon sellers) shoot products on a phone against a bedsheet or kitchen tile. Every channel then wants a different image: Amazon wants a pure-white main image, Instagram 4:5, Stories 9:16, WhatsApp catalog and Meesho 1:1. Zomato quoted restaurant partners INR 4,000–5,000 for a professional menu shoot ([Business Upturn](https://www.businessupturn.com/business/zomato-urges-restaurants-to-ditch-ai-generated-food-images-to-avoid-misleading-customers/)). Generic AI photo tools fix the look but can redraw the product, and buyers punish that: Zomato banned AI-generated dish images from Sept 16 2024, citing customer complaints, higher refunds and lower ratings ([Inc42](https://inc42.com/buzz/zomato-bans-use-of-ai-generated-images-by-restaurant-partners/)).

RealStage: upload one phone photo. Your **real** product is cut out once, placed on AI-generated stages made by 3 different image models side by side, optionally relit by AI with your original pixels locked back on top, and exported as a 4-file marketplace kit. Cloudinary does storage, cutout, generation, compositing, cropping, archiving, delivery and the data layer. Vercel runs thin API routes plus three small sharp steps (alignment check, _core erosion, Amazon white check).

Hackathon: Pixels to Products (HackIndia x Cloudinary). **Track 2: Generative Content Workflows** ("Cloudinary AI image generation, including variations and model choice, inside an existing pipeline"). The event page says Cloudinary must be "a core part of the product, not just for storing images."

## What Makes This Cool

- **Same product, 3 models, side by side.** Each card is your product on a stage generated by a different model family, with model_id, seed and credit cost printed under it. Model choice is on screen.
- **Pixel-Lock relight.** One click sends the chosen card to an image_to_image edit model for real light and contact shadows, then Cloudinary layers your original cutout pixels back at identical geometry. An alignment score proves the AI didn't move or reshape the product; if it did, the card falls back to the exact composite and says so.
- **Cloudinary is the backend.** No database. Assets, tags, context, structured metadata, Admin/Search API and archive generation are the whole data layer.
- One photo in, 4 channel-ready files out, in under 90 seconds.

## Recommended Approach

### Flow and generation-call accounting

| Step | What happens | Generation calls |
|---|---|---|
| 1. Upload | Signed server upload to `realstage/u/<sessionId>/<rand>` | 0 |
| 2. Cutout | Server materializes the cutout as its **own asset** `<id>_cut` by uploading the derived URL `e_background_removal/e_trim/f_png` of the original (trimmed; the single canonical cutout string). Paid once (75 transformations); every later output derives from `_cut`, never re-runs removal. Server also stores a `_core` version: alpha eroded 2px + 1px feather (sharp), used only for the Pixel-Lock overlay. | 0 |
| 3. Stage grid (default) | 3 cards = product composited onto 3 **library stages**, each stage made earlier by a different model family (text_to_image). Pure Cloudinary overlay URLs. | **0** |
| 4. Relight (click, 1 card) | Composite of the chosen card → `image_to_image` edit model, `image_size` 1:1 2K, prompt "relight the product to match the scene, add a natural contact shadow, keep composition and product identical" → alignment check → overlay `_core` at same geometry. Output materialized as asset. | **1** |
| 5. New stages (click, optional) | User prompt → `text_to_image` on 3 models (one per family), 1:1 2K, seed pinned → 3 new stages with default geometry. | **3** |
| 6. Export kit | 4 derived files materialized as assets tagged `kit-<kitId>`; zip via Cloudinary archive by tag; share page `/k/<kitId>`. | 0 |

The 3 models shown are fixed after the Oct 1 check (target: `flux-2-pro`, `nano-banana-2`, `recraft-v4` for stages; relight edit model = bake-off winner among `flux-2-pro-edit`, `nano-banana-2-edit`, `gpt-image-2-edit`). If fewer than 3 families work on the account, the grid shows 2 cards plus a "more models" card linking a pre-rendered comparison.

### Placement geometry

- Each stage asset stores context `anchor_x, floor_y, max_w, max_h` (fractions 0–1 of the stage).
- **Library stages**: generated with a fixed prompt template ("empty surface, eye-level camera, clear product area centered in the lower half, soft directional light from the left, no objects in center") and geometry authored by hand while curating (6–8 stages, ~2 min each).
- **Live stages**: same template, default geometry `anchor_x 0.5, floor_y 0.8, max_w 0.5, max_h 0.6`.
- **Fit rule**: scale `_cut` (already `e_trim`med) to fit inside `max_w × max_h` preserving aspect; product bottom sits on `floor_y`, horizontal center on `anchor_x`. Server computes pixel x/y/w from `_cut` dimensions (returned by the upload response) and builds `l_<cut>,c_fit,w_<w>/fl_layer_apply,g_north_west,x_<x>,y_<y>`. The same numbers are reused for the Pixel-Lock overlay.
- `max_w ≤ 0.5` guarantees a centered 9:16 crop (0.5625 of width) contains the product.

### Alignment check (Pixel-Lock gate)

- Inputs: relit output (before overlay, resized to the composite's size if the aspect matches) and the composite it was made from. Region: the product mask bounding box from `_cut` alpha.
- Algorithm (sharp, Vercel route): grayscale, mean-normalized **normalized cross-correlation** inside the mask, plus the same on a 12px ring outside the mask edge (detects shift/rescale ghosts).
- Pass: mask NCC ≥ 0.85 and ring NCC ≥ 0.6 (starting thresholds, calibrated in the bake-off).
- Output aspect ≠ input aspect, or check fails → the card shows the exact composite with the note "AI relight moved the product, showing exact composite". Credits spent are still counted.
- UI label: "Alignment 0.93 · real pixels locked". It measures "did AI keep your product where it was", not "how real it looks".

### Edge handling

`_core` (eroded 2px, feathered 1px) is the locked layer, so a thin band of relit pixels replaces the original background spill at the edge. Declared limitation: translucent or fringed products (glass, saree tassels) may show a halo; bake-off inspects halos explicitly.

### Kit outputs (explicit formats for downloads, f_auto only for previews)

| File | Size | Transform (from `_cut` or the materialized final) |
|---|---|---|
| Amazon main | 2000×2000 | `_cut`: `e_trim/c_pad,w_1700,h_1700,b_white/c_pad,w_2000,h_2000,b_white/f_jpg,q_95` → product longest side = 85%; no AI scene. Server samples the 4 corners + 4 edge midpoints with sharp and asserts RGB 255,255,255; falls back to `f_png` if not. |
| Instagram post | 1080×1350 | final: `c_crop,ar_4:5` centered on `anchor_x` → `c_scale,w_1080/f_jpg,q_90` |
| Story / Reel cover | 1080×1920 | final: `c_crop,ar_9:16` centered on `anchor_x` → `c_scale,w_1080/f_jpg,q_90` |
| WhatsApp / Meesho | 1080×1080 | final: `c_scale,w_1080/f_jpg,q_90` (Meesho exact spec unverified; square ≥1000px is the common guidance) |

Stages are 1:1 at 2K (2048px), so every crop has ≥1080px width without upscaling. On-screen previews use `f_auto,q_auto`.

### Data model (all in Cloudinary)

- Tags: `realstage`, `session-<id>`, `stage`, `lib` (library stages), `gen-YYYYMMDD` (every generation call's output), `cut-YYYYMMDD` (every cutout), `kit-<kitId>`, `exp-YYYYMMDD` (expiry date).
- Context: generation provenance (model_id, prompt, seed; set automatically by the gen API) + placement geometry on stages.
- Structured metadata (authoritative for display; created Oct 1 by `npm run setup:metadata` via Admin API): `rs_product_name` (string), `rs_stage_model` (string), `rs_alignment` (number), `rs_pixel_locked` (enum yes/no). Set on the materialized final asset only.

### Caps, counters, abuse

- Counter store: **Cloudinary tags counted via Admin API** (`resources_by_tag gen-YYYYMMDD` / `cut-YYYYMMDD`). Enforced in the API route before calling Cloudinary. Tolerance: concurrent requests can overshoot a cap by 1–2; accepted.
- Per-session soft caps: signed httpOnly cookie (5 uploads, 2 relights, 1 new-stage fan-out). Bypassable by clearing cookies; the global caps are the real guard.
- Global daily caps (derived from the budget below): cutouts 60/day, generation calls = judge reserve ÷ days remaining ÷ avg cost (computed at deploy, ~5/day at 50 credits). When a cap hits, relight and new stages disable with "Live AI budget used for today, library stages still work", and the zero-credit path continues.
- Upload limits: JPG/PNG/WebP/HEIC, ≤10 MB, enforced client and server side. Cloudinary applies EXIF rotation.
- Moderation: accepted risk for v1. Assets use random unguessable public IDs; I can delete any bad asset by tag. Revisit if abuse appears.
- Header counter "Live AI tries left today: N" = global cap minus today's `gen-` count. After each generation response, the server logs `limits.addons_quota[].remaining` to confirm real remaining credits.

### Async handling

- Generation: `async: true` → 202 + task_id → client polls `GET /api/task/:id` every 2s (the route calls `/v2/generate/.../tasks/:id`), UI timeout 90s with a "still working / retry" state. Every route returns in <10s, well inside Vercel function limits.
- Cutout: upload-from-derived-URL may return 423 while processing → server retries 3× with 3s backoff; client shows "cutting out your product…".

### Inputs and failure states

- Cutout sanity: if alpha coverage < 3% or > 95% of the frame → "Couldn't find a clear product. Retake on a plain surface with space around it." Multiple items in one shot are treated as one product group (declared limitation).
- Generation error / quota 403 → card error state with retry; zero-credit path unaffected.

### Retention and sharing

- Session assets tagged `exp-<today+7>`; `npm run cleanup` (and a Vercel cron if time allows) deletes expired tags. Library stages are permanent.
- Share link `/k/<kitId>` = page listing the 4 kit files + zip, readable by anyone with the link, until expiry. Upload screen shows: "Demo: your photos are stored for 7 days, then deleted."

### R2-1 — consistency

**Problem**

> The Fit rule says to scale '_cut (already e_trimmed)', and it computes x/y/w from the _cut dimensions returned by the upload response. Step 2, however, materializes _cut from 'e_background_removal/f_png' with no e_trim, and the Amazon main transform applies e_trim again. An untrimmed _cut keeps the full phone-photo frame with transparent padding. The fit, floor placement and 9:16 containment math would then use the whole frame instead of the product, so the product shrinks and floats above floor_y. _core (derived from _cut) must also share _cut's exact dimensions, or the reused Pixel-Lock coordinates will not line up.

**Remedy**

> Add e_trim to the materialization in step 2 (for example e_background_removal/e_trim/f_png), or compute the geometry from trimmed dimensions. Also state that _core is derived from the trimmed _cut with identical pixel dimensions.

### R2-2 — consistency

**Problem**

> The global generation cap '~5/day at 50 credits' does not follow from the budget. The judge reserve is 18 credits over Oct 3-10 (8 days), about 2.25 credits/day. The budget table implies about 1.5-2 credits per call (bake-off 14 credits for 9 calls, library 12 credits for 6-8 stages), so the formula yields about 1-1.5 calls/day, not 5. The wireframe shows ~4-6 credits per stage. A single per-session '1 new-stage fan-out' (3 calls) therefore exceeds a whole day's reserve. The cap also counts calls while per-model and 2K costs vary.

**Remedy**

> If fewer than 3 families work, the grid shows a 'more models' card 'linking a pre-rendered comparison'. The design does not say where that comparison comes from if the missing family cannot run on the account, or who produces it and when.

**Remedy**

> Say what the comparison contains and how it is produced (for example rendered in the bake-off from families that did work, or drop the card and show 2 cards).

### R2-19 — clarity

**Problem**

> Step 5 produces 3 new stages, but the design does not say where they appear: whether they replace the grid cards or go into the wireframe's 'Saved stages' strip. It also does not say whether they persist per session, expire with exp-, or become visible to other users. The 'saved-stages strip' is referenced in the wireframe note but never defined in the flow.

**Remedy**

> Define the UI placement of new stages, their scope (session-only, tagged session- and exp-, never lib), and what the Saved stages strip lists.

### R2-20 — feasibility

**Problem**

> Live stages get a fixed default geometry (floor_y 0.8, anchor_x 0.5, and so on) on the assumption that the model obeyed the 'clear product area centered in the lower half' prompt. Generation often places objects or horizons differently, so products will float or overlap scene objects on live stages. Library stages avoid this only because their geometry is authored by hand.

**Remedy**

> Include live-stage placement quality in the bake-off's 3 stage tests, and either declare it a limitation on live stages or add a simple user nudge (for example drag or a floor slider).

### R2-21 — completeness

**Problem**

> The claim that 'max_w <= 0.5 guarantees a centered 9:16 crop contains the product' holds only if anchor_x lies within [max_w/2, 1 - max_w/2] and the crop window is clamped to the frame. Hand-authored library geometry has no such constraint, and 'c_crop,ar_9:16 centered on anchor_x' needs an explicit computed x offset in Cloudinary.

**Remedy**

> Add the authoring constraint on anchor_x relative to max_w. State that the crop x is computed server-side as clamp(anchor_x*W - cropW/2, 0, W - cropW) and passed with g_north_west.

### R2-22 — completeness

**Problem**

> The Amazon white check samples only corners and edge midpoints, which fall in the padded margin and are white by construction. It never checks the background inside the trimmed product box, where semi-transparent background-removal remnants blend into the white. The f_png fallback can also keep transparent pixels in that region, which is not pure white.

**Remedy**

> Flatten transparency onto white explicitly (b_white applied to the alpha, or a flatten step) for both JPG and PNG outputs. Extend the check to sample the area outside the product mask within the trimmed box, or state that it is out of scope.

### R2-23 — clarity

**Problem**

> Upload limits accept HEIC, but 'HEIC polish' is a Could-ship item. The design does not say what works if the polish is cut. Browsers other than Safari cannot preview HEIC in the upload column, and sharp prebuilt on Vercel usually lacks HEIC decoding if any server step touches the original.

**Remedy**

> State the HEIC baseline: Cloudinary converts on upload and all previews use f_auto delivery URLs, so no browser or sharp HEIC decoding is needed. Alternatively, drop HEIC from accepted inputs until the polish ships.

Rules that protect the credits:
1. **Zero-spend development.** `GEN_MODE=mock` is the default in dev and tests: `/api/generate` returns an existing library asset after a 3 s delay with the same response shape. Real calls need `GEN_MODE=live`, which is only set in Vercel production and in `scripts/bakeoff.ts` / `scripts/setup.ts --generate`.
2. **Automated tests and `scripts/smoke.ts` never call `/v2/generate`.** They use library stages. A test that hits the real generation endpoint is a bug.
3. **Don't use the Console playground** ("Generate with AI") for experiments. Every click there spends from the same 50.
4. **Model choice for credits.** Use the cheapest tier per family that passes the bake-off (`tier: "standard"` or `mode: auto` + `preference: "economy"`). Read per-model costs from the Console's "Change model" panel before spending anything. Reading it is free.
5. **Resolution rule.** Generate at **1K** unless the probe shows 2K costs the same.
   With 1K (1024 px) stages, the kit is built like this, using free transformations:
   - Instagram 4:5: crop 819×1024 → `c_scale,w_1080` + `e_sharpen`.
   - Story 9:16: the 1:1 stage scaled to 1080 wide, padded to 1080×1920 with `b_blurred:400:15`.
   - WhatsApp: 1080².
   - Amazon: built from `_cut`, unaffected.
   This replaces "stages 1:1 at 2K" in Kit outputs and steps 4–5.
6. **Global credit cap = 15 (the judge reserve)**, production pool only, enforced atomically by slot claims (see Outside Voice Round X2/X3), counted across days. When it is hit, the UI shows "Live AI paused to save credits". The library path and kit keep working, so the app never breaks for a judge.
7. **Trip-wire.** If `limits.addons_quota.remaining` < 8 on any response, the server flips to paused, even if the ledger disagrees.
8. **Credits may reset monthly.** Treat the 50 as total until judging ends, and don't count on a reset.
